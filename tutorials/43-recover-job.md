# 43｜等待超时或下载失败后，继续原任务

你已经点过生成，现在终端超时、Agent 会话断开，或者 API 显示成功但找不到文件。先不要再次运行生成命令。要判断的是原请求现在处于哪个阶段。

> 状态：正文已完成；未执行线上付费生成或宿主实连。依据：[S1 / S2 / S3](../SOURCES.md)。本地测试范围见 [验证报告](../verification/REPORT.md)。

## 第一种：已经有任务 ID

把它当作原任务的唯一查询入口：

```bash
PREDICTION_ID='替换为已返回的真实任务ID'
atlas generate get "$PREDICTION_ID" --json
```

如果还在处理，继续查询或等待原任务：

```bash
atlas generate wait "$PREDICTION_ID" --timeout 10m --json
```

不要仅根据 Shell 退出码判断结果。终态为 failed 或服务端 timeout，与本地 wait 达到时间上限，是不同情况。终态失败也不自动授权换模型重试。

给 Agent 的恢复指令可以这样写：

> 这个 Atlas 任务的 ID 是【填入真实 ID】。只查询和继续等待该任务，不要重新生成、切换模型或账户。远程完成后尝试取回已有产物；如果保存本地失败，告诉我远程链接、具体阶段和未完成事项。

## 第二种：生成已完成，但文件没保存下来

比较远程 `outputs` 与本地 `saved_files`，再检查实际路径是否存在、文件是否非空。一次远程成功不证明下载成功。

继续原任务的读取/下载路径即可，优先让 CLI 根据真实媒体类型决定文件后缀：

```bash
atlas generate wait "$PREDICTION_ID" --json
```

需要明确本地路径时，先核对真实格式，再使用：

```bash
OUTPUT='./recovered/result.mp4'
mkdir -p './recovered'
atlas generate wait "$PREDICTION_ID" --output "$OUTPUT" --json
```

上例仅用于已知输出确实为 MP4 的任务。图片、音频、3D 应使用真实后缀；不要通过改后缀冒充格式转换。再次失败时保留输出 URL 与错误阶段，不要调用生成来修复下载问题。

## 第三种：提交超时，连 ID 都没有拿到

这是“是否已受理未知”，不应写成“生成失败”。先保留原回执、发生时间、账户、所选模型与脱敏后的请求信息。检查有没有成功写到本地的 submit.json、终端输出或其他可靠记录。

使用独立 MCP 且实际暴露 `atlas_list_predictions` 时，可以在同一账户查询历史，再用 `atlas_get_prediction` 核对候选任务。但相同模型和相近时间并不一定足以唯一匹配；证据不够时应继续保留未知状态，或通过平台支持渠道核对。不能猜一个 ID。

本次核对的 CLI 指南没有提供可以在这里直接代替上述历史查询的统一命令，因此本教程不编造 `atlas jobs history` 之类的命令。

新的一次生成调用可能被当作新任务计费。本地回执减少了丢失风险，但不能解决请求已到服务端、响应尚未保存时进程崩溃的所有情况。严谨的自动化还需要服务端幂等与请求核对能力。

## 第四种：登录或供应商访问错误

```bash
atlas auth status --json
atlas doctor --json
```

本地过期时由用户重新完成登录。本地仍为 logged_in，却收到供应商访问错误时，不要擅自更换 dev 环境、API 地址、账户或凭据。也不要把同一个原任务拿到另一个账户继续查询后，错误解释为任务不存在。

## 恢复结果应该怎么报告

可以按下面四句话交付：原任务 ID 是什么；目前确认的服务端状态是什么；产物已在哪里找到；本地保存或内容验收还有什么未完成。若始终没有得到 ID，就说受理结果仍未知，不宣称未扣费，也不宣称肯定扣费。

这一篇的验收目标是减少错误重提交，不是保证所有任务最终成功。能准确停在未知状态，比自动再花一笔钱更可靠。
