# 35｜交付前检查容器、分辨率、帧率、时长和音轨

本篇建立交付前的技术检查。它回答文件是否存在、媒体流是什么、是否满足指定规格、能否完整解码；不会回答创意是否优秀、字幕是否准确或产品是否变形。把两类检查分开，才能避免“FFmpeg 没报错”被当成最终作品合格。

## 写明期望规格

从需求中取出容器、分辨率、时长、是否必须有声音，以及可接受的误差。不要看到文件是 MP4 就假定它是 H.264，也不要仅看编码头把可变帧率认定为恒定帧率。旋转标记、像素长宽比、色彩空间与 HDR 信息都可能影响实际显示。

> 检查交付目录里的视频，只做本地读取与解码，不上传、不重生成。先核对实际宽高、时长、音轨和容器，再检查整片能否解码；对帧率、旋转和色彩的未知情况明确说明。把技术检查和人工视觉/声音检查分开记录。

## 基础命令与严格检查

```bash
python3 scripts/media_audit.py ./assets/final.mp4
python3 scripts/media_audit.py ./assets/final.mp4 \
  --width 1080 --height 1920 --duration 15 --tolerance 0.2 \
  --require-audio --decode --output tutorial-output/final-audit.json
```

这里的 15 秒±0.2 秒是示例验收，不是所有平台规范。脚本返回 0 表示本次指定的检查通过，1 表示发现规格或解码问题，2 表示无法完成检查。没有传某个规格就不会检查该项；`content_review` 始终为 `not_performed`。

默认全片解码上限为 180 秒，需要更长检查时显式使用 `--decode-timeout`。达到本地上限应报告未完成解码，不能将其解释为视频坏了或解码已通过。只读元数据时没有遍历每一帧。

## 看报告里容易被忽略的字段

检查 `video` 和 `audio` 数组，而不是只看第一个数值。`avg_fps` 和 `r_fps` 不一致时记录原因待查；二者相同也不能单独证明 CFR。`sample_aspect_ratio` 非 1:1 或包含 rotation 时，编码宽高与显示宽高可能不同。缺失 duration 不可自动当作零秒内容。

如果需要固定编码、音频采样率或码率，先读报告，再在可信转换流程中明确设置并复检；本包脚本不会替你悄悄修复所有问题。两次转换造成的损失也应纳入结果说明。

## 将验收产物与运行日志分开

把最终文件与必要的人工审核记录放进专用交付目录，先确认没有 API key、客户未授权资料或内部 URL，再建立文件清单：

```bash
python3 scripts/manifest.py --root ./delivery --output ./delivery/manifest.json
```

`manifest.py` 记录字节数和 SHA-256，拒绝符号链接；它不做敏感信息识别，也不能证明版权或内容准确。发送前后比对摘要，可以检查传输是否改变了文件。

## 不通过时从相应阶段修复

下载中断先重取原任务结果，码流损坏检查源文件或重新下载；规格不符再考虑本地转码；运动形变属于内容问题，可能涉及重新生成。每一类应保存不同原因，避免一个笼统失败码让自动化系统把整条链重跑并重复付费。

最终报告应同时显示技术检查结果、人工审核结果和未验证事项。客户只要最终成片时，不必把所有内部日志一起打包。
