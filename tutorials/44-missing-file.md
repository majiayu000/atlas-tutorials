# 44｜API 显示成功，为什么本地还是没有文件

服务端显示 succeeded，电脑上却找不到文件，通常说明生成和交付处在不同阶段。本篇从回执、远程产物、下载和本地路径逐层检查，目标是找回已经生成的结果，不再花钱生成一次。

## 先取得原任务的完整事实

保留任务 ID 和原账户，读取实际结果：

```bash
PREDICTION_ID='替换为原任务ID'
atlas generate get "$PREDICTION_ID" --json
```

检查状态是否真为完成，以及任务类型是否应该产生媒体文件。ASR 可能主要返回文本，3D 可能返回多个网格和预览，不能对所有任务套用“一个 MP4”的交付规则。MCP text 内容或 REST data 包装也不能直接喂给只识别 CLI 根字段的脚本。

> 这个任务已经远程完成但我没找到本地文件。请只检查原任务的 outputs、saved_files 与实际路径，保留账户，不提交新生成。区分没有产物、链接不能取、下载失败和文件保存到别处；给出明确已确认与未确认事项。

## 对照三个位置

`outputs` 是服务端返回的产物引用；`saved_files` 是客户端宣称保存的文件；文件系统里的真实非空文件才证明落盘。缺少 saved_files 可能意味着使用了不下载模式、宿主没有文件工具或下载失败，不代表服务端未生成。

从真实路径核对文件，不根据 URL basename 猜测。使用 Python 包装器时，CLI 工作目录是对应的 run 目录；相对路径应以那个工作目录解析，不一定是你启动终端时的目录。跨设备访问也不能把远端机器路径当本地路径。

## 只恢复下载

先核实输出类型，再让 CLI 取回原任务结果。没有硬性命名要求时使用默认扩展名：

```bash
atlas generate wait "$PREDICTION_ID" --json
```

若确知输出是 MP4，再指定新的安全路径：

```bash
mkdir -p tutorial-output/recovered
atlas generate wait "$PREDICTION_ID" \
  --output tutorial-output/recovered/video.mp4 --json
```

不要覆盖不明旧文件；单任务多产物时检查全部输出，并确认 CLI 对自定义路径的处理。扩展名只用于命名，不会把 WebM 转成 MP4。

## 链接失败时检查原因

临时链接可能过期，代理或网络策略也可能阻止访问。先重新查询原任务取得当前可用引用，再通过平台支持的取回方式处理；不能保证每次查询都会刷新链接或恢复被清理的文件。浏览器能够访问而服务器不能访问时，排查各自网络和认证环境。

不要为了下载向 CDN 发送 Atlas API key，也不要关闭 TLS 校验。受控下载器应限制协议、来源、大小和保存路径；返回 HTML 错误页也可能产生一个非空 `.mp4` 文件，因此还要用 `media_audit.py --decode` 核对真实内容。

## 正确的结束报告

可以交付“生成已完成，文件已恢复并通过解码，内容未人工审查”；也可以明确“服务端完成，但产物链接不可用，尚未保存本地”。远程完成却没有任何可用输出时，应保留未解决状态并核对平台，不杜撰路径或产物。

下载修复与模型重新生成是两件事。只有内容本身未达要求且用户批准新尝试，才进入新的生成操作。
