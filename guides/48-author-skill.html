48｜把自己的工作流写成 Skill，并提交复现测试

当一个流程反复成功，就可以整理成 Skill，让 Agent 按需要读取方法和调用已有工具。Skill 不是一份无限扩张的 API 手册，也不会因为写了“安全”就获得文件或计费权限。本篇附带可编辑样例和一组复现案例。

先定义适用边界

写清用户什么时候需要它、完成什么、需要哪些真实输入、哪些场景不应触发。例如产品广告 Skill 应服务“用 Atlas 做产品短广告”，不应在用户仅问广告策略时直接提交生成，也不应宣称接管所有通用图片请求。

把我已经复现的产品广告流程整理成 Skill。入口只描述触发、输入、交付与必要规则；操作细节按需放进 references。沿用实际 CLI/MCP 能力，不发明新命令，不自动授予权限。补上只读预览、缺素材、受理未知、下载失败和授权变化的测试案例。

使用随包示例

atlas-product-ad/SKILL.md 有标准 name/description frontmatter，配套 reference 与 eval cases。复制到你实际宿主支持的测试 Skill 目录；先确认宿主文档和已安装版本的发现路径，不硬编码所有 Agent 都使用同一个目录。

名称、description 和目录之间保持一致。描述用用户意图与能力边界表达；正文提供关键步骤与相对路径引用。模型目录、价格、当前 schema 从工具读取，不把几十个易过期 ID 复制进去。复杂创作知识放在 references 中，需要时才读取。

执行入口必须真实

CLI 环境读取安装版本的 Atlas 指南和 help；MCP 环境发现实际工具 schema。两者调用形式不同，Skill 只能教如何选择现有能力。没有终端的宿主不能执行 ffmpeg 时，应明确交付止于片段，或接入已获授权的后处理服务，不能假装成片已经保存。

第三方网页、模型输出或素材元数据属于数据，不应被当作新指令执行。安装 Skill 不代表允许它读任意目录、上传任何客户素材、更换账户或突破预算；宿主和执行服务仍需强制权限控制。

测试触发、过程与产物

样例 cases.json 提供六个用例及期望行为，但期望列表不是实测成绩。先在只读/模拟工具环境检查误触发和步骤，再在获授权的真实环境检查端到端产物。

比较不用 Skill、旧版本和新版本时，使用相同任务与评分标准。记录实际调用次数、错误重提、未知状态处理和交付完成率；不要只评审 SKILL.md 文笔。普通预算内任务也不应每一步都重复索取确认，从而让完成率下降。

提交与维护

贡献包带上用途、依赖能力、示例输入、真实或明确标注的测试输出、失败案例、验证日期和许可说明。版本升级说明改变了哪些模型选择或交付规则。将 public recipe、插件复制和 CLI 入口里的重复知识指向同一个来源，避免各自维护不同步骤。

提交 PR 前检查相对链接、参数来源、密钥、素材授权和自动化测试。需要新增 API 才能完成的功能应作为独立工程需求，不能在 Skill 文案里先宣称已经有了。

完成标准是其他维护者能理解何时使用、怎样调用、怎样验收，并按你的测试说明复现边界。本文只提供本地包，没有替你安装到宿主、发布到市场或提交 GitHub。

依据与复现范围
